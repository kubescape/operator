# OperatorCommand configuration-scan outcome contract

Research snapshot: 2026-10-23. Source revisions: [operator `9f88e2e`](https://github.com/kubescape/operator/tree/9f88e2e48b4dfd6cac9daf2605300ca2161937ff), [Kubescape scanner `32da7c7`](https://github.com/kubescape/kubescape/tree/32da7c733db298b2f3af4163772f1514ab2d0685), and [Helm chart `7b9f178`](https://github.com/kubescape/helm-charts/tree/7b9f178872f8f7fcc1218b3441c6696d4146c159). The relevant branches are also present in published [operator v0.2.197](https://github.com/kubescape/operator/releases/tag/v0.2.197) and [Kubescape v4.0.16](https://github.com/kubescape/kubescape/releases/tag/v4.0.16); the audit's isolated release-source reproductions are outside this source-contract note.

## Observed contract and failure

The operator watches `OperatorCommand` resources, attaches the CRD to a session, and dispatches the decoded command. The CRD schema and Go type distinguish `status.completed` from `status.error`; the status writer sets `completed=true` and sets `error` only when passed an error. Its `WithSuccess()` option is recorded but not read by the writer. [Watcher](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/watcher/commandshandler.go#L41-L83), [status writer](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/utils/types.go#L34-L116), [CRD schema](https://github.com/kubescape/helm-charts/blob/7b9f178872f8f7fcc1218b3441c6696d4146c159/charts/kubescape-operator/crds/operator-command.crd.yaml#L55-L89).

There are two false-success points for CRD-triggered configuration scans. First, a successful asynchronous `POST /v1/scan` dispatch queues a status poll and returns `nil`, after which the generic request handler immediately writes `completed=true,error=nil`. Second, the later poll checks only whether `/v1/status` is `busy`; every other response type is recorded as success. The poll interval is 40 seconds. [Dispatch and poll](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/kubescapehandler.go#L126-L211), [generic completion branch](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/handlerequests.go#L195-L249).

The scanner's status handler reads only its active-scan map: an absent ID returns HTTP 200 with `type:notBusy`. The worker removes the ID from that map on success, failure, cancellation, and panic. Thus `notBusy` means no active entry; it does not establish a successful scan. The [OpenAPI description](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/docs/swagger.yaml#L336-L355) calls it a completion check, and the [response type definitions](https://github.com/kubescape/opa-utils/blob/v0.0.315/httpserver/apis/v1/apis.go#L20-L33) describe `busy`/`notBusy` as server activity. [Status handler](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandler.go#L149-L192), [active state](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/serverstate.go#L15-L37), [worker terminal paths](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L128-L230).

`GET /v1/results?id=<scanID>` does distinguish a persisted failure (`500`, `type:error`) from a result (`200`, `type:v1results`), but a missing artifact returns `204`. It reads and validates the full report JSON; with the default `keep=false`, an explicit-ID read deletes that artifact. This makes it a costly steady-state outcome probe and makes missing results ambiguous. [Results handler](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandler.go#L384-L433), [result-file reader](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L352-L401), [query contract](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestparser.go#L33-L55).

The `kubescape operator scan configurations` CLI currently reports only that an operator trigger was accepted; its adapter sends an HTTP request to the operator and returns on HTTP 200. It does not itself wait for a scan result, so the CRD status defect should not be described as a demonstrated CLI exit-code defect. [CLI message](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/cmd/operator/configscan.go#L20-L45), [adapter](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/core/core/clusterconnector.go#L101-L143).

## Selected compatible contract

The local scanner change adds an optional, scan-ID-correlated `outcome` field to the existing `GET /v1/status` JSON envelope, preserving HTTP 200 and the existing `type:busy|notBusy` meanings. `busy` omits `outcome`; `notBusy` reports `succeeded`, `failed`, `cancelled`, or `unknown` and includes the requested or resolved scan ID. Failed, cancelled, and panicked scans expose generic error text rather than the underlying scan error. The local operator change accepts success only for a matching scan ID with `type:notBusy` and `outcome:succeeded`. This additive design follows the existing [response envelope](https://github.com/kubescape/opa-utils/blob/v0.0.315/httpserver/meta/v1/datastructure.go#L104-L120), [status behavior](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandler.go#L151-L192), and [operator response parser](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/kubescapehandlerhelper.go#L104-L124).

A bounded in-memory terminal record keyed by scan ID is the lightweight source of truth. The local change retains the latest **1024 user scan outcomes** in completion order; metrics scrapes do not consume this budget. It publishes each terminal outcome in the same state lock operation that clears `busy`, including success, failure, queued cancellation, running cancellation, and panic. An absent or evicted ID returns `unknown`, never success. The error field uses generic `scan failed`, `scan cancelled`, or `scan panicked` text. This follows the [baseline active-only state](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/serverstate.go#L15-L96), [worker terminal branches](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L128-L230), and [existing redacted error artifact writer](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L608-L639).

The in-memory record is lost on scanner process restart. The implemented response for an unremembered ID is `unknown`; the operator records an unavailable-outcome error rather than success. Result-file presence alone cannot replace this contract because reads/deletes remove files and cancelled scans deliberately remove artifacts; the chart mounts result directories as pod-local `emptyDir` volumes. A durable ledger remains outside this change. [Baseline state initialization](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/serverstate.go#L209-L214), [file removal](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L403-L449), [cancellation](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L168-L182), [chart volumes](https://github.com/kubescape/helm-charts/blob/7b9f178872f8f7fcc1218b3441c6696d4146c159/charts/kubescape-operator/templates/kubescape/deployment.yaml#L310-L320).

For **new operator + old scanner**, an absent `outcome` produces an unavailable-outcome error on the CRD. The operator does **not** call `GET /v1/results` as a compatibility fallback: that endpoint reads the full posture report, explicit-ID reads can delete it unless `keep=true`, and `204` cannot establish success or failure. For **old operator + new scanner**, the additive fields are ignored and false success remains possible until the operator updates. Scanner-first rollout makes the new outcome available before the new operator needs it; the interim old-operator window is not fixed. These mixed-version limits follow the [old operator terminal branch](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/kubescapehandler.go#L126-L156), [scanner results contract](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandler.go#L384-L433), and [status parser](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/kubescapehandlerhelper.go#L104-L124).

The local operator change stops its **immediate** terminal-success patch after async dispatch and writes `started=true,completed=false,payload=<scanID>`. It retries a failed pending status patch immediately and during later polls. On restart, an unfinished command with a valid stored scan ID is eligible for watcher replay even after the normal 30-minute age cutoff; its receiver is registered before the startup list begins, its original start time is retained, and the handler resumes polling instead of dispatching a second scan. A pending command with no recorded scan ID cannot use this recovery path, so the dispatch-to-pending-patch window remains an at-least-once delivery risk. The poll retries transient HTTP/parse failures at 40-second intervals and records an error after **three consecutive failed attempts**; a valid busy or terminal response resets that counter. A failed Kubernetes terminal status patch is retried with the cached outcome without another scanner request. A terminal `unknown`, mismatched ID, missing outcome, or unrecognized type fails closed without a results fetch. [Generic completion branch](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/handlerequests.go#L225-L234), [baseline terminal-only writer](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/utils/types.go#L64-L116), [startup list and age rule](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/watcher/commandswatcher.go#L62-L75), [watcher dispatch](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/watcher/commandswatcher.go#L117-L140).

The existing scanner callback reports `completed`/`failed` and the scan ID, but it is disabled unless explicitly configured, delivery is best effort, and the implementation calls for a poll/reconciliation fallback. Replacing the status poll with callbacks alone therefore would not establish durable terminal status. [Callback producer and contract](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L58-L82), [callback configuration and limits](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L657-L713).

## Public test seams and decisions

- Scanner HTTP seam: `POST /v1/scan` then `GET /v1/status?id=<exact ID>` through success, forced scan error, in-flight cancellation, queued cancellation, panic, unknown ID, result deletion, and scanner process restart. Existing test seams use `scanImpl` and the real handler; status lifecycle tests are in `serverstate_test.go`, and callback lifecycle tests cover terminal paths. [Handler setup](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandler.go#L116-L128), [injection seam](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/requestshandlerutils.go#L43-L48), [current status tests](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/serverstate_test.go#L373-L425).
- Operator CRD seam: intercept the actual status subresource patch for dispatch and terminal polls. Check pending status with the scan ID, success/failure/cancel/unknown classification, three consecutive status-read failures, old-scanner fail-closed behavior, and replay of a pending stored scan ID without a second POST. This is test scope, not a claim that a live CRD journey has passed. The baseline writer patches the Kubernetes status subresource through the dynamic client. [Status patch](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/utils/types.go#L64-L116), [dispatch and poll](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/kubescapehandler.go#L126-L211).

Proof boundary: this note records the source contract and the selected local design. It does not establish a live failed-scan CRD journey, hosted deployment, or released mixed-version upgrade. The 1024-entry memory limit, scanner restart loss, 40-second poll, three-attempt transient retry bound, and scanner-first rollout should be checked against deployment needs before release. [Baseline poll interval](https://github.com/kubescape/operator/blob/9f88e2e48b4dfd6cac9daf2605300ca2161937ff/mainhandler/kubescapehandler.go#L25-L28), [baseline scanner state](https://github.com/kubescape/kubescape/blob/32da7c733db298b2f3af4163772f1514ab2d0685/httphandler/handlerequests/v1/serverstate.go#L15-L37), [chart volumes](https://github.com/kubescape/helm-charts/blob/7b9f178872f8f7fcc1218b3441c6696d4146c159/charts/kubescape-operator/templates/kubescape/deployment.yaml#L310-L320).
